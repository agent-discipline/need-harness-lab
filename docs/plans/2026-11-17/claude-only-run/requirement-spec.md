## 1. 목표·대상 (필수)

`payment-settlement/claude/`의 세 조건(1 minimal · 2 detailed · 3 harness-auto) × 10회 = 30회를 Claude만으로 끝까지 실행해, 조건별 완료까지의 토큰·추정 비용·완료율·품질을 결과 표로 낸다. 실험 진행자(실행 관리·판정·피드백 전달·기록)는 Opus 에이전트가 맡고, 메인 세션이 그 에이전트를 브리핑하고 결과를 회수한다.

- A. 준비 — Claude 쪽을 본 실험이 가능한 상태로 보강하고 새 프로토콜 버전(`payment-settlement-v3-claude`)으로 동결.
- B. 파일럿 1회(결과 제외).
- C. 본 실험 10사이클.
- D. 결과 정리.

## 2. 경계·불변식 (필수)

- 세 조건의 구현 모델(Opus 5.5, effort high)·도구(웹 도구 포함)·자원 한도·상한은 같다. 차이는 입력 상세도와 절차뿐이다. 하네스 조건만 PM(Fable 5.2)·서브에이전트·하네스 훅을 갖는다. 하네스 조건의 구현·테스트·리뷰 워커는 Opus 5.5이고, 탐색 워커는 하네스 정의(Sonnet)를 따른다. 대리 사용자는 Opus 5.5다.
- 하네스 조건의 리뷰는 Opus 워커와 Fable 5.2 두 리뷰어다(codex 자리 대체). 이 대체는 실제 하네스와 다른 점으로 결과에 명시한다.
- run마다 새 컨테이너·새 세션·새 DB. 다른 run의 코드·실패 이력이 넘어가지 않는다.
- 실험 진행자는 구현에 개입하지 않는다 — 판정 결과와 `prompts/feedback.md`가 정한 형식의 피드백만 전달한다. 진행자·판정 어댑터·대리 사용자의 토큰은 역할별로 분리 기록한다.
- 상한: run당 input+output 2,000만 토큰 · 8시간 · 피드백 30회. 먼저 닿으면 `CENSORED_*`로 끝내고 보존한다. 실패 run을 결과에서 지우지 않는다.
- 판정 기준과 요구사항은 동결 후 바꾸지 않는다. 바꾸면 프로토콜 버전을 올리고 전 조건 재실행이다.
- 사용량 집계는 요청 단위이고 부모·서브에이전트 중복 합산이 없다. 관측하지 못한 사용량은 0으로 채우지 않고 `usage_complete=false`로 남긴다.
- 자격증명 값은 저장소·로그·기록 어디에도 남기지 않는다.

## 10. 종료 경로 설계 (2026-11-17 추가 — 사용자 합의: "설계대로 구현 진행하자")

배경: 리뷰 3회차가 `review unresolved`로 끝났고, 신규 채택 10건 중 7건이 run이 끝난 뒤의 경로에 몰렸다. 이 경로는 사람이 손으로 옮기던 절차에 스크립트를 덧붙인 것이라 전체 설계가 없었다. 사용자 결정(2026-11-17): "종료 경로 설계부터 하고 권고대로 진행". 아래가 그 설계이고, 합의 뒤 구현한다. 리뷰는 이 범위만 1회 추가한다(상한 초과분 — 사용자 승인).

### 10.1 순서 (고정)

```
마지막 턴 종료(또는 상한 차단)
  → 판정 실행: 진행자가 판정기·어댑터를 실행하고 산출물과 관측 메모를 기록 폴더에 저장
  → 판정표 작성: 메인이 산출물을 직접 읽고 기록 폴더의 verdict.json을 쓴다
  → normalize → capture_turn(남은 턴 기록 — 기록 폴더의 파일이 여기서 마지막으로 바뀐다)
  → 종료 기록: finish_run.py가 판정표·장부·manifest에서 종료 상태와 증거 칸을 도출해 run.json에 기록(근거 해시는 이 시점 값)
  → discard → commit_run.py
```

### 10.2 종료 상태와 증거 칸의 원천 (불변식)

- 종료 상태 PASSED·FAILED는 인자로 받지 않는다. 판정표에서 도출한다. `INVALID_INFRA`만 인자로 받는다(사유 필수).
- 판정표(`verdict.json`)는 C01~C20 각각에 `PASS`·`FAIL`·`PARTIAL`·`NOT_RUN` 중 하나와 근거 산출물 경로를 적는다. 종료 기록은 근거 파일이 실제로 있는지 확인하고 해시를 함께 남긴다. 20개가 모두 `PASS`일 때만 통과다(`PARTIAL`·`NOT_RUN`은 통과가 아니다 — `evaluation/README.md` 결과 해석).
- `commit_run.py`가 PASSED에 요구하는 네 칸은 종료 기록이 아래 원천에서만 쓴다. 원천이 없거나 거짓이면 그 칸은 false이고, 손으로 true를 쓰는 경로는 없다.

| 칸 | 원천 |
|---|---|
| `all_acceptance_passed` | 판정표: 20개 모두 PASS이고 근거 파일이 모두 존재 |
| `usage_complete` | 실행 폴더(`.runs/<id>`)에서 그 자리에서 계산한 run 장부의 `usage_complete`(기록 폴더의 사본은 종료 기록 시점에 아직 없다) |
| `all_role_models_verified` | 실행 폴더의 manifest와 요청 이벤트로 역할별 모델을 합의 모델과 대조(동결 때 쓰는 검사와 같은 함수). 그 조건에 있어야 할 역할이 관측되지 않으면 false. 탐색 워커의 Sonnet 예외는 요청 단위로 검사 |
| `isolation_verified` | 그 run의 self-test가 통과했고, 그 run의 도구 목록이 동결 파일에 기록된 그 조건의 도구 목록과 같음. 세 조건 간 비교는 동결 때 한 번 하고 run마다 다시 하지 않는다(선검증 반영) |

- **판정표는 메인이 쓴다(사용자 결정 2026-11-17).** 사용자: "하네스로 판정하지말고 해당 내용을 너가 직접 읽어서 감독관인것처럼 다 판정하도록 하는게 맞는 거 같아." 메인의 해석: run의 최종 통과 여부(C01~C20 판정표)는 표본이 아니라 30건과 파일럿 전부를 메인이 판정기 산출물을 직접 읽고 판정한다. 진행자는 판정기·어댑터를 실행해 산출물을 저장하고 시나리오별 관측 메모를 붙이는 데까지 하며, 통과 여부를 정하지 않는다. run 도중 구현자에게 돌려주는 피드백(판정기가 확인한 실패 목록의 전달)은 진행자가 계속 맡는다 — 이 구분은 메인 해석이므로 사용자에게 확인한다.
- 종료 기록이 기계로 확인하는 것은 근거 파일의 존재와 해시, 판정표의 작성자 표시(`judged_by`)까지다. 판정 내용이 맞는지는 기계로 확인하지 못한다.
- 통과했는데 증거 칸이 하나라도 false면 종료 상태는 PASSED로 쓰되 커밋 단계가 막는다(지금 `commit_run.py` 동작 그대로). 우회 경로는 없다. 진행자는 거기서 멈추고 원인을 `issues.md`에 적어 메인에 보고하며, 메인이 사용자에게 보고한다(다음 사이클은 시작하지 않는다).
- `INVALID_INFRA`는 구현과 무관한 실행 환경의 실패(Docker·호스트·판정 도구 자체의 고장)일 때만 쓴다. 판정 실행이 구현 때문에 실패한 것은 FAIL이다(`evaluation/README.md` 결과 해석). 사유와 근거 파일을 함께 기록하고, 진행자가 제안하면 메인이 확인한 뒤에 기록한다.
- 종료 기록의 대상은 턴이 한 번 이상 나간 run이다. `NOT_STARTED`·`SETUP_FAILED`는 종료 기록이 거부한다 — 준비 실패의 복구는 기존 절차(runbook "사이클 준비 실패 복구") 그대로이고 이 설계의 범위 밖이다.
- 상한에 호출 전 차단으로 끝난 run은 새 턴 없이 그 시점까지의 기록으로 판정·종료 기록·커밋한다(첫 턴은 항상 나간 뒤이므로 기록할 턴이 있다).
- 종료 기록은 run당 한 번이다. 이미 종료 상태가 있는 기록에 다시 실행하면 거부한다. 정정이 필요하면 `--supersede --reason`으로만 하고, 이전 `run.json`을 지우지 않고 옆에 보존한다.
- **통과 여부는 판정표만으로 정하고, 상한 기록은 표시로 붙는다(2026-11-18 리뷰 감사 반영 — 이전의 "턴일 때만 완료 + 초과", "호출 전 차단 + 전부 PASS는 거부"를 대체).** 판정을 메인이 하게 되면서, 진행자가 도중에 실패로 보고 다음 호출을 시도해 상한에 막힌 run도 최종 판정에서는 전부 PASS일 수 있다. 그런 run을 거부하면 종료 상태를 얻을 길이 없고, 판정표를 고치게 하면 판정이 왜곡된다. 그래서: 판정표가 전부 PASS이면 상한 기록이 있든 없든 PASSED다. 상한 기록이 있으면 `cap_reached=true`와 함께 상한의 종류·시점(호출 전 차단 / 호출 뒤 초과)·호출 종류(턴 / 대리 사용자)·초과량을 run.json에 옮겨 적는다(결과 표에서 "완료", "완료 + 상한 도달", "완료 + 초과"를 구분). 통과하지 못했고 상한 기록이 있으면 `CENSORED_*`다. 상한 기록 자체는 고치지 않는다.
- 판정표의 각 기준은 근거가 있어야 한다: PASS·FAIL·PARTIAL은 실제로 있는 근거 파일 1개 이상, NOT_RUN은 사유(note). 이를 채우지 못한 판정표로는 종료 기록을 할 수 없다(통과가 아닌 종료 상태도 마찬가지).

### 10.3 파일럿

- 파일럿은 본 실험과 run id·기록 위치가 다르다: run id `claude-pilot-NN`, 기록 `claude/docs/pilots/<run id>/`. `init --pilot`이 manifest에 표시한다.
- 기록 도구(capture_turn·finish_run)는 manifest의 표시로 위치를 정하고, 기록 폴더의 run id와 실행 run id가 다르면 거부한다.
- `commit_run.py`는 파일럿을 다루지 않는다(본 실험 30건 전용, Codex판과 바이트 동일 유지 — 수정 금지). 파일럿 기록은 일반 docs 커밋으로 남긴다.
- 파일럿 통과 증거(`freeze_readiness`의 pilot 검사)는 지금처럼 실행 폴더(`.runs`)의 턴·사용량·모델과 manifest로 판정한다(절차가 끝까지 도는지를 보는 검사이고 품질 합격을 요구하지 않는다). 파일럿의 판정표와 종료 기록은 보고 ②의 자료이며 동결 증거에 들어가지 않는다. 파일럿 재판정은 `--supersede`로 한다.

### 10.4 평가 비용 (진행자·판정 어댑터)

- 사용자 결정(2026-11-17, 메인 권고 채택): 진행자 비용은 **실험 전체 단위의 평가 비용 장부**에 기록하고 조건별 비용과 run 상한에 넣지 않는다. 진행자가 쓴 피드백의 토큰을 따로 떼어 실험군에 넣는 것은 측정할 방법이 없어 결과 표의 한계로 적는다(세 조건이 같은 진행자·같은 방식이라 조건 간 비교는 유지).
- 장부: `claude/docs/results/evaluation-cost.jsonl`, 한 줄 = 진행자 세션 1개 또는 어댑터 작성 1건(같은 세션이 어댑터를 여러 번 작성하면 건마다 한 줄 — 건을 구분하는 표시를 함께 적는다). 칸: 역할, 세션 식별자, 모델, 토큰(네 카운터 또는 합계), 숫자의 출처, 맡은 run id 목록, 시각. 덧붙이기만 한다.
- 기록 주체는 메인이다(진행자 에이전트의 완료 알림 usage). 진행자가 어댑터를 직접 썼으면 진행자 한 줄에 포함되고 어댑터 줄을 따로 쓰지 않는다(중복 방지 — 줄에 그 사실을 적는다).
- run 장부의 `evaluation_cost` 블록과 run 단위 기록은 없앤다. 종료 기록은 평가 비용을 요구하지 않는다(진행자 사용량은 세션이 끝나야 나오므로 종료·커밋 순서와 충돌).
- 누락 점검은 결과 정리(task 10)에서 한다: 본 실험 30건과 파일럿의 모든 run id가 어느 한 줄의 run 목록에 들어 있어야 하고, 빠진 run은 "평가 비용 미기록"으로 표에 드러난다.

### 10.5 그 밖의 채택 지적

- 동결 파일 경로를 명시했는데 파일이 없으면 `init`은 거부한다. 동결 전 실행은 기본 위치에 동결 파일이 없을 때만 된다(U1).
- `recovery` 턴은 이어 가는 턴과 같은 프롬프트(해시 일치)만 보낸다(U9).
- 대리 사용자 호출은 그 run의 manifest에 고정된 이미지와 같은 이미지로만 실행한다(U10).
- 비용 인자는 0 이상의 유한수만 받는다(U6). runbook의 종료 상태 표를 실제 분기와 맞춘다(U5).

### 10.6 금지·검증

- 금지: `commit_run.py`·`lab.py`·`payment-settlement/codex/**`·공유 `measurement/`·`recording/`·`evaluation/` 수정. 유료 호출.
- 검증: 기존 테스트 전부 통과 + 명세 기반 테스트(구현 미열람 워커)로 10.2~10.5의 불변식 각각 + 이 범위만 Opus 리뷰어 ∥ codex 리뷰 1회와 감사.
- load-bearing 가정(확인됨 2026-11-17 — `codex/docs/pilots/detailed-01/`의 `acceptance-http.json`은 C01~C20 각각에 status·scope·관측 결과를, `acceptance-faults.json`은 C13·C14·C17을, `acceptance-audit.json`은 전수 대조 집계를 담는다. HTTP 결과는 `PARTIAL`(HTTP_ONLY)로 나오므로 DB·은행 대조와 합쳐 판정하는 사람이 필요하다 — 메인 판정과 맞는다): 판정기 산출물만으로 C01~C20 각각의 PASS 여부를 진행자가 판정표에 옮길 수 있다(`evaluation/README.md`는 상위 controller가 모은다고만 적음). 9월 Codex 파일럿 기록(`codex/docs/pilots/detailed-01/` — 읽기만)으로 착수 직후 확인한다.
- 설계 선검증(codex, 2026-11-17): 충돌 4건·원천 점검·빠진 경로 3건·단순화안 1건 → 위 문구에 반영(장부를 실행 폴더에서 계산, 격리 칸의 정의, INVALID_INFRA 기준, 대상 run의 범위, 파일럿 증거와 재판정의 분리).
