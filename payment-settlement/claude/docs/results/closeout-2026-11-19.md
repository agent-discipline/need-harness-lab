# Claude 판 실험 중단 기록 (2026-11-19)

결제·정산 API 과제로 "하네스가 실제로 필요한가"를 세 조건에서 비교하려던 Claude 판 실험을, 본 실행을 한 번도 유효하게 마치지 못한 채 중단한다. 이 문서는 무엇을 했고, 무엇이 관측됐고, 왜 멈췄는지를 적는다.

## 요약

- 예비 실행(파일럿) 4회와 본 실행 1회를 돌렸다. 유효하게 끝난 본 실행은 0회다.
- 파일럿에서 본 방향은 하나다. 하네스 조건은 판정 피드백을 한 번도 받지 않은 상태에서 20개 항목 중 19개가 계약에 맞았다. 최소 지시 조건은 첫 완료 선언 때 0개였고, 판정 피드백을 8번 받은 뒤 19개가 됐다.
- 이 관측은 조건마다 1회이고 두 실행의 규칙과 모델 구성이 서로 달라, 하네스의 효과를 보여 주는 근거로 쓸 수 없다. "하네스가 있으면 평가자와 더 적게 오가고 원하는 결과에 도달한다"는 사용 경험과 같은 방향이라는 정도까지만 말할 수 있다.
- 중단 사유는 비용이다. 실행할 때마다 실행 환경이나 실험 규칙의 새 결함이 나왔고, 끝까지 가도 조건당 1회라 결론을 낼 수 없었다.

## 무엇을 비교하려 했나

같은 과제(결제 승인, 멱등성, 정산, 장애 복구, 부하 기준을 갖춘 API)를 세 조건으로 구현하게 하고, 합격 기준 20개(C01~C20)의 통과 수와 토큰, 시간을 비교하려 했다.

| 조건 | 입력 | 모델 |
|---|---|---|
| 1번 (최소 지시) | 짧은 요청만 준다 | Opus 5.5 하나 |
| 2번 (상세 지시) | 요구사항, 자원, 부하 기준 문서를 함께 준다 | Opus 5.5 하나 |
| 3번 (하네스) | 2번과 같은 입력에, 하네스 v4.3의 훅과 절차(인터뷰, 명세 합의, 작업자 분리, 듀얼 리뷰)를 적용한다 | PM은 Fable 5.2, 작업자는 Opus 5.5, 두 번째 리뷰어는 Fable 5.2 |

에이전트가 완료를 선언하면 평가자가 합격 기준을 확인하고, 통과하지 못한 항목을 하나씩 알려 준다. 이 왕복을 전 항목 통과나 상한(토큰 1억 5천만, 에이전트 턴 시간 8시간, 판정 피드백 30회)까지 반복하는 설계였다. 3번 조건에서 PM이 구현 전에 내는 질문에는 사람 대신 답하는 별도 에이전트(대리 사용자)가 답했다.

## 실행 기록

| 실행 | 조건 | 결과 | 토큰 | 끝난 이유 |
|---|---|---|---|---|
| 파일럿 01 | 3번 | 무효 | 276만 | 두 번째 리뷰어가 컨테이너 안에서 인증되지 않음 |
| 파일럿 02 | 3번 | 무효 | 529만 | 실행기가 백그라운드 작업의 대기 상한(10분)을 풀지 않아 작업자가 강제 종료됨 |
| 파일럿 03 | 3번 | 19 / 20 | 8,930만 | 당시 토큰 상한(2천만)을 턴이 끝난 뒤에만 검사해서, 상한의 약 4.5배에 이른 뒤 종료 |
| 파일럿 04 | 1번 | 19 / 20 | 7,380만 | 8시간 상한. 그중 절반 이상이 판정과 대기 시간이었음 |
| 본 실행 1회차 | 3번 | 무효 | 3,973만 이상 | 턴 컨테이너가 프로세스 수 제한(512개)에 걸려 종료됨 |

다섯 실행의 장부 합계는 2억 1,087만 토큰이다. 인증과 동작만 확인하는 짧은 실행(스모크) 가운데 기록된 것 42만을 더하면 약 2억 1,130만이다. 실험을 진행하고 판정한 세션과 실행기를 고친 세션이 쓴 토큰은 이 합계에 들어 있지 않다. 구독 토큰으로 실행해 청구된 금액은 없고, 주간 사용량에서 차감됐다.

2번 조건은 파일럿과 본 실행을 한 번도 돌리지 못했다.

## 파일럿에서 관측한 것

| | 파일럿 03 (하네스) | 파일럿 04 (최소 지시) |
|---|---|---|
| 첫 판정 때 통과 수 | 19 / 20 (완료 선언 전, 상한으로 멈춘 상태에서 판정) | 0 / 20 (첫 완료 선언 뒤) |
| 최종 통과 수 | 19 / 20 | 19 / 20 |
| 19개가 될 때까지 받은 판정 피드백 | 0회 | 8회 (전체 10회) |
| 구현 전 질의응답 | 질문 27개, 대리 사용자와 3번 오감 | 없음 (질문 0건) |
| 토큰 | 8,930만 | 7,380만 |
| 시간 | 4시간 41분 (첫 턴 시작부터 마지막 턴 끝까지) | 4시간 2분 (턴 시간의 합) |
| 통과하지 못한 항목 | C20 (부하) | C20 (부하) |

- 최소 지시 조건은 첫 완료 때 API 경로가 계약과 달라(`/payments`, 계약은 `/api/payments`) 평가자의 업무 요청이 모두 404였다. 그 뒤 피드백을 한 번에 한 항목씩 받아 고쳤고, 통과 수는 0, 7, 8, 9, 11, 14, 15, 19로 늘었다. 남은 C20에는 피드백을 2번 더 받았지만 통과하지 못했다.
- 하네스 조건은 구현 전에 질문을 내고 명세 합의를 거쳤다. PM은 완료를 선언하지 않았다. 마지막 턴을 질문으로 끝냈고, 그때 토큰 상한을 넘은 상태라 다음 턴을 보내지 않았다. 그 상태로 판정했을 때 부하 항목을 뺀 전부가 통과했다. 무효가 된 본 실행 1회차도 같은 순서로 진행됐다(질문 22개, 명세 합의, 작업 3건 완료, 리뷰 도중 종료).
- 하네스 조건은 평가자와의 왕복은 없었지만 구현 전 질의응답이 있었고, 토큰도 더 썼다(작업자 6,020만, PM 2,681만, 리뷰어 222만). 총비용이 줄었다고 볼 근거는 없다.
- 부하 항목(C20)은 돌려 본 두 조건 모두 통과하지 못했다. 파일럿 03은 50 RPS 구간의 응답 시간과 k6가 보내지 못한 요청 수(dropped iterations)가 기준을 넘었다. 파일럿 04는 50 RPS 구간에서 바로 확정되지 않은 응답이 54건 나왔고, 100 RPS 스파이크 구간의 응답 시간과 보내지 못한 요청 수가 기준을 넘었다. 5xx 응답은 두 조건 모두 없었고, 부하가 끝난 뒤의 전수 대조에서 유실과 이중 처리는 없었다.

### 이 관측을 근거로 쓸 수 없는 이유

- 조건마다 1회다. 같은 조건을 다시 돌렸을 때 결과가 얼마나 달라지는지 모른다.
- 두 파일럿의 규칙이 달랐다. 파일럿 03은 옛 토큰 상한에 걸려 완료 선언도, 피드백 왕복도 없이 끝났고, 파일럿 04는 바뀐 상한에서 왕복을 10번 했다.
- 조건 사이에 하네스만 다른 것이 아니다. 3번은 PM이 Fable 5.2이고 1번은 Opus 5.5 하나다.
- 파일럿의 목적은 실행 절차의 결함을 찾는 것이었고, 실제로 매번 절차를 고쳤다.
- 과제가 하나다.

## 왜 중단했나

- **결함이 줄지 않았다.** 다섯 번의 실행에서 서로 다른 결함이 다섯 가지 나왔다. 셋은 실행 환경의 결함이고(리뷰어 인증, 백그라운드 작업 종료, 프로세스 수 제한), 둘은 실험 규칙의 설계 문제다(토큰 상한을 검사하는 시점, 시간 상한에 판정 시간이 섞임). 하나를 고치면 다음 실행에서 다른 것이 나왔다.
- **고칠 때마다 드는 비용이 컸다.** 실행기, 실행 입력을 고정하는 스크립트, 실행 전 점검 스크립트를 합쳐 테스트 포함 1만 5천 줄이 넘는다. 한 곳을 바꿀 때마다 리뷰, 스모크, 입력 재고정을 거쳤다. 끝까지 간 실행은 한 번에 4~8시간이 걸렸다.
- **끝까지 가도 결론이 약했다.** 본 실행의 첫 묶음은 조건당 1회다. 통계로 쓸 만큼 반복하려면 수십억 토큰이 필요하다.
- **부하 기준을 통과한 조건이 없었다.** 돌려 본 두 조건이 각 1회씩 모두 통과하지 못했다. "전 항목 통과"를 기준으로 삼으면 어느 조건이든 상한에서 끝나게 된다.

하네스 전체를 한 과제로 한꺼번에 재는 설계가 이 비용을 만들었다. 같은 조직의 [compaction-experiment](https://github.com/agent-discipline/compaction-experiment)는 질문 하나를 작은 과제로 재서 이틀 만에 쓸 수 있는 결과를 냈다.

## 남긴 것

- **실행 환경에서 확인한 사실** (`docs/runbook.md`): `claude -p`는 마지막 응답 10분 뒤 백그라운드 작업을 강제 종료한다(환경 변수로 풀 수 있다). `--resume`으로 이은 세션의 사용량은 세션 누적값이다. Claude Code는 Bash 자식 프로세스에 인증 토큰을 넘기지 않는다.
- **실행기와 판정 절차** (`runner/`, `scripts/`, `docs/runbook.md`): 컨테이너 격리, 역할별 사용량 분리, 상한 강제, 구현마다 DB 스키마에 맞춰 쓴 판정용 변환 코드.
- **기록**: 파일럿은 `docs/pilots/claude-pilot-01~04/`, 무효가 된 본 실행은 `docs/experiments/3/core1/`.

## 다음에 한다면

하네스의 규칙을 하나씩 따로 잰다. 파일럿의 관측에서 나온 첫 후보는 이것이다.

> 구현 전에 명세 합의 단계를 거치면, 첫 완료 때 계약에서 벗어난 항목이 줄어드는가.

작은 과제 여러 개와 싼 모델로, 첫 완료 시점의 계약 일치 수만 잰다. 조건 사이에 모델은 같게 둔다. 부하 기준처럼 통과한 조건이 없는 항목은 넣지 않는다.
