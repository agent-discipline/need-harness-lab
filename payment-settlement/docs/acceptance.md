# 판정 계약과 시나리오

상태: 판정 설계 동결 후보. `evaluation/k6/smoke.js`는 기반 서버 검증, `payments.js`는 주요 업무 검증의 실행 가능한 시작점이다. 전체 장애/DB 판정기는 실험 개시 전 완성·negative-control 검증이 필요하다. 현재 skeleton의 업무 테스트 실패는 정상이다. 이 파일의 체크표 자체를 실행 완료 증거로 취급하지 않는다.

## 공통 조건

시나리오 시작마다 깨끗한100만 사용자 DB와 은행 journal, 동일 seed, 별도 workload namespace. 구현자는 평가 파일·threshold·fixture를 변경할 수 없다. 평가자는 응답 및 DB·은행 journal을 교차 대조한다. 같은 오류를 재현하는 최소 요청과 관측 사실만 구현자에게 반환하며 해법은 전달하지 않는다.

|---|---|---|---|
| C01 | P0 | 정상 결제1건 | 201·영속 SUCCEEDED·차감/은행/원장 각1건 |

C13/C14는 k6만으로 충분하지 않다. 평가자 측 장애 주입 스크립트로 정확한 실패 구간을 확인하고 k6는 동시 트래픽을 담당한다. C17은 제어 가능한 Clock/seed timestamp 또는 평가자 주입 fixture로 검증하고 벽시계 자정 대기로 대체하지 않는다. 구현별 SQL adapter는 평가자가 읽고 검증하며 구현자가 제출한 쿼리 결과만 신뢰하지 않는다.

## 부하 SLO — 사전 고정 후보

파일럿으로 host가 아래 부하 발생량을 낼 수 있는지 확인한 뒤 세 조건 시작 전에 확정한다. 목표가 불가능하면 전 조건 시작 전에만 protocol version을 올려 수정한다.

1. 워밍업30초/10RPS(결과 집계 제외), 서로 다른 사용자로 정상 결제50RPS·5분.
2. 정상 결제95% + 기존 성공 멱등 replay5%의 고정 traffic. p95<500ms, p99<1500ms, 예상치 못한5xx<0.1%, dropped_iterations=0.
3. spike100RPS·30초 이후 정상50RPS·60초 복귀. 큐/풀 대기가 유한하고 복구30초 이내, 거래 유실·이중 처리0.
4. soak30RPS·15분. steady RSS 증가가 초기 안정구간 대비20%를 넘으면 원인 조사, 연결 누수/교착/OOM0. 모든 final PENDING은 fault 해제 후30초 안에 소진.
5. 용량탐색25→50→100→200RPS 각2분. 합격 종료와 별도로 **SLO를 유지한 최대 sustainable RPS** 보고. 최고 처리량을 쫓아 토큰 종료를 무한 연장하지 않는다.

timeout/422/409가 의도된 시나리오는 예상 응답을 별도로 판정한다. 전역 http_req_failed 임계치에 정상 거절을 오류로 합산하지 않는다. correctness 시나리오와 latency workload는 분리한다. 동일키 hot-key와 사용자 hot-account는 균등분포 workload와 별도 보고한다.

## 데이터 불변식과 품질

기초: 사용자 count=1,000,000, 대행사 count=1,000, orphan=0. 원장 debit/credit 보존, 성공별 은행 journal 대응1개, 실패별 차감0, payment/settlement item 참조 누락0, 사용자 balances≥0, 대행사 순정산액과 잔액 증가 일치. 표본 조회 외 **전수 집계 쿼리** 증거를 보관한다.

조건명·원경로·하네스 문서·프롬프트 이력을 제거한 코드와 공통 계약 packet만 독립 리뷰어에 제공한다. 설계 품질은 Claude Fable의 독립 블라인드 리뷰 1회로 각0..2점을 판정한다: HTTP/업무/영속 레이어 분리, 은행 port 교체성, 명시적 상태·거래경계, 금액/멱등성 메서드 응집성, 오류/복구 경로 테스트, 중복로직·과도한 추상화 억제. 총12점 중10점 이상 및 어느 항목도0이 없어야 최종 완료. 지적은 코드 위치·근거와 함께 보존하며 미해결 지적을 통과 처리하지 않는다. 리뷰 모델은 파일럿에서 관측한 `claude-fable-5-1`으로 고정하고, 리뷰 사용량은 구현 사용량과 별도 집계한 뒤 전체 비용에도 포함한다. 3번 하네스 내부 리뷰와 이 공통 최종 리뷰는 별개이다. 메서드 길이만으로 품질을 판정하지 않는다.

판정기 검증은 중복 차감·다른 payload 재사용·원장 누락·잘못된 정산을 고의로 만드는 작은 negative control을 실패시키는 방식으로 한다. skeleton404가 검증에서 통과하면 평가기 결함이다.
