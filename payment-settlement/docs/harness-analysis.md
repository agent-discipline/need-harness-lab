분석 대상은 해당 작업트리의 `src/core.md`, `playbooks/review.md`, `playbooks/refactoring.md`, `hooks/set-state.sh`, `settings.json`이다. 아래 `파일:줄`은 원본 위치이며, 원본을 수정하거나 배포하지 않았다. HEAD와 작업트리 일치 여부는 실행 전 별도로 고정해야 한다.

## 원본에서 확인한 auto 절차

1. 인터뷰 후 명세를 작성한다. 명세에는 목표·대상, 경계·불변식, 기준소스, 금지영역, 검증 방법, stakes의 6칸과 자율성, 핵심 가정이 필요하다. 이미 명시된 항목은 재질문하지 않는다 (`src/core.md:19`, `:21`, `:22`, `:23`).
2. 명세 합의 후 `SPEC=1`, 이후 `MODE=auto`를 기록한다. auto는 합의 후 자율 실행을 뜻한다. 검증이나 리뷰가 생략되지 않는다 (`src/core.md:25`, `:28`, `:32`, `:49`). `set-state.sh`는 승인 판단기가 아니라 기록 수단이고 답변이 선행해야 한다. `mode` 전이에 `SPEC=1`을 요구한다 (`hooks/set-state.sh:6`, `:105`, `:109`).
3. 결제는 원본 기준 높은 stakes다 (`src/core.md:66`). 실행물에 대해서는 설계 선검증, 구현 diff를 보지 않는 별도 테스트 설계 워커, 듀얼 리뷰 최대 3루프를 요구한다 (`src/core.md:83`, `:86`, `:87`). 설계 문서만 다루는 작업은 별도 상한이 있다 (`:89`).
4. PM은 인터뷰·명세·작업 분해·브리핑·게이트·합의·stakes·종합·log 작성을 소유한다. 독립 구현·테스트·리뷰·탐색은 워커가 맡을 수 있다. 워커는 task ID, 기준 SHA, 읽은 파일, 실행한 검증과 결과, 미완료, 원시각을 반환한다 (`src/core.md:92`, `:94`, `:95`, `:96`).
5. 리뷰는 누적 diff, untracked 내용, spec 원문, 관련 심볼 검색 결과와 읽기 전용 미러를 양쪽에 동일하게 전달한다. 구현 의도, 대화, 메인 판단, ledger는 독립 리뷰 입력에서 제외한다 (`playbooks/review.md:14`, `:60`, `:61`). 절차는 병렬 리뷰 → 메인 종합 → 종합 감사 → 수정·테스트 → 필요시 재리뷰다 (`:10`, `:11`, `:63`, `:64`, `:65`, `:66`).
6. 높은 stakes의 종료는 채택했으나 미수정인 finding 0, 현재 루프 신규 채택 finding 0, 적용되는 렌즈 검증 근거 충족이다. 3루프를 초과하면 `review unresolved`로 중단하고 미해결 상태를 보고한다 (`playbooks/review.md:68`, `:76`). 따라서 k6만 통과했다고 원본 하네스 완료 조건을 충족하지 않는다.
7. 리팩토링은 보존 동작 합의 → 특성테스트 baseline green → 그룹핑·경계 합의 → 소단위 변환마다 green → 합의된 특성테스트 전건 green과 공개 계약 diff 0을 입증하는 순서다 (`playbooks/refactoring.md:16`, `:20`, `:29`, `:33`, `:38`). 기능 변경은 별도 명세 합의로 분리한다 (`:51`).
8. spec와 log는 작업 프로젝트에 기록하고, 완료 시 측정로그에 워커 모델도 기록한다 (`src/core.md:110`, `:111`, `:112`).

## 저가 워커 가정과 실제 정책

검토한 활성 규칙에서 저가 워커를 기본으로 선택하는 정책은 발견되지 않았다. 명시된 기본값은 **Opus·high**다 (`src/core.md:95`). 리뷰는 **Opus 워커 + Codex**를 병렬로 사용하고 (`playbooks/review.md:61`), Codex 리뷰 호출은 reasoning effort를 **medium**으로 지정한다 (`:113`, `:115`). 이는 저가 구현 워커를 선택하는 모델 라우팅 규칙과 다르다.

원본은 다른 모델이 독립 신호를 제공한다는 근거를 든다 (`playbooks/review.md:5`). 모든 역할을 Sol-high로 바꾸면 컨텍스트 분리는 유지할 수 있지만, 다른 모델을 사용한 검증의 효과까지 재현했다고 주장할 수 없다.

## 3번 실험에서 명시할 이식 차이

| 항목 | 원본 | 이번 주 비교의 이식 기준 |
|---|---|---|
| 메인·구현 모델 | Claude 메인, 워커 기본 Opus·high | 1·2·3 모두 실제 실행 가능한 동일 Sol 모델 ID와 high를 고정하고 기록 |
| 리뷰 모델 | Opus + Codex, Codex 리뷰 medium | 서로 격리된 동일 Sol-high 리뷰어 2개와 별도 종합 감사 역할. 모델 다양성은 재현하지 못한다는 편차 기록 |
| 사용자 응답 | 사람이 인터뷰·명세·모드에 응답 | 실험 관리자가 사전 고정 답변표로 사용자 역할 대행. 답변과 판정의 입력·출력 토큰도 계상 |
| auto 게이트 | Claude hooks 및 상태 CLI | Codex 실행 관리자가 동일 상태 순서를 기록하고 구현 시작 전 검증. 강제되지 않은 규칙은 절차 준수 여부로 평가 |

| 리뷰·테스트 격리 | spec 기준, 구현 의도·대화 제외 | 별도 프로세스와 허용 파일 복사본 사용. blind 테스트 워커에게 구현 소스/diff 미제공 |
| 완료 | 하네스 리뷰 종료식 + 검증 | 공통 기능·동시성·부하·정합성·구조 품질 게이트와 해당 하네스 종료식 모두 만족 |

3번 조건 이름은 **Claude 하네스 auto의 Sol 모델 통제 이식**으로 표시한다. 원본 하네스 그대로 실행한 결과와 혼동하지 않는다. 모델 통제 주 비교와 실제 혼합 모델 운영 비용 비교는 별도의 질문이다.

실험 관리자와 3번 PM도 역할을 구분한다. 관리자는 공통 정답 계약과 답변표를 소유하고, 3번 PM이 질문하고 명세·게이트·작업 분해를 소유한다. 관리자가 다른 조건에서 발견한 해법을 3번 응답에 추가하면 정보가 누출된다. 2·3번의 초기 상세 프롬프트는 같은 내용을 사용하고, 질문 답변 및 검증 결과로 추가 제공한 정보량을 기록한다.

## 훅·세션·캐시 경계

`settings.json:3`은 SessionStart, `:13`은 UserPromptSubmit, `:27`은 PreToolUse, `:55`는 PostToolUse 훅을 Claude 경로 `~/.claude/hooks/`로 연결한다. 이 파일을 Codex 폴더에 복사하는 것만으로 같은 강제가 작동한다고 가정할 수 없다. 원본 자체도 Bash 내부 의미·MCP·워커 쓰기는 훅 관찰 범위 밖이라고 설명한다 (`src/core.md:12`, `:39`). 이식에서는 실행 관리자 게이트와 실제 프로세스/파일 접근 격리를 검증해야 한다.

원본 리뷰 호출의 `--ephemeral` 사용(`playbooks/review.md:113`)을 서버의 프롬프트 캐시 비활성화 증거로 해석하지 않는다. 새 세션, 대화 미상속, 별도 작업트리, 별도 데이터 볼륨은 구현 내용 누출을 줄이는 통제다. 서비스 제공자 캐시는 별도 계층이므로 공식 인터페이스로 통제 가능 여부를 확인하고 cached input을 측정해야 한다. 실제 보장과 측정 방식은 실험의 격리·토큰 정책에 따른다.

원본에서도 read-only 샌드박스는 읽기 경계가 아니라 쓰기 제한이며, 미러와 프롬프트가 읽기 절차를 형성한다고 명시한다 (`playbooks/review.md:115`). 실험에서는 프롬프트만으로 강한 파일 접근 격리를 보장했다고 기록하지 않는다.

## 실행 전에 고정할 증거

- 원본 SHA, 작업트리 상태, 사용하는 규칙 파일의 해시 및 이식 차이 목록.
- 실제 모델 ID·reasoning effort·CLI 버전·각 역할의 모델, 합산 대상 세션/워커 ID.
- 질문 답변표, 요구사항 공개 순서, 공통 평가 기준과 테스트 해시.
- 리뷰별 입력 packet 해시, 컨텍스트 격리 방식, findings와 종료 판정.
- spec 합의·auto 선택의 대행자와 시각, 중단·차단·미완료 기록.

이 문서는 실험 설계의 근거이며, 본 실험 실행이나 하네스 적용 완료를 뜻하지 않는다.
