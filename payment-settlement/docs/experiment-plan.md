# 실험 계획 v1

작성일: 2026-09-23. 실행 정책: 별도 Codex 컨테이너 + exec/resume 대화 제어, goal 비활성, observed-cache. 상태: PREPARATION. 주제: payment-settlement. 실제 돈이나 금융망을 사용하지 않는 재현 실험이다.

## 가설과 비교 대상

상세 요구사항은 재작업을 줄일 수 있고, 하네스는 사전 질문·명세·독립 검증에 토큰을 추가 지출하는 대신 결함과 후기 수정 비용을 줄일 수 있다. 어느 쪽이 유리한지는 측정한다. 결과가 나오기 전에 우열을 선언하지 않는다.

| 항목 | 1 minimal | 2 detailed | 3 harness-auto |
|---|---|---|---|
| 최초 요청 | 짧은 업무 요청 | requirements.md 전문 | 2와 동일한 전문 |
| 공통 환경 정보 | 빌드·연동 fixture·레이어드·자원 한도 | 동일 | 동일 |
| 추가 절차 | 구현 후 검증 | 상세 입력 후 검증 | 하네스 인터뷰·명세·합의·워커·검증 |
| 후속 입력 | 고정 우선순위의 미충족 항목 **1개** | 미충족 항목을 묶은 구조화 프롬프트 | PM이 검증·리뷰를 종합해 지시 |
| 사용자 역할 | 평가자가 최소 피드백 | 평가자가 프롬프트 수정 | 대리 사용자 에이전트가 질문에 답변 |
| 업무 코드 | 레이어드 Kotlin | 동일 | 동일 |

1번도 모델 자체의 추론·도구·자발적 테스트는 허용한다. 숨은 상세 계약을 처음부터 제공하지 않는다. 공통 fixture에 포함된 연동 계약은 모두 동일하게 공개하며, 따라서 완전히 정보 없는 모델 성능 실험은 아니다. 1↔2는 입력 상세도와 피드백 방식이 함께 달라지는 실용적 방법론 비교다. 상세도만의 인과 효과가 필요하면 후속 실험에서 피드백 정책을 동일하게 맞춘다.

## 모델과 공정성

- 요청 모델 표기: `gpt-sol-high`. 실행 모델 기본 선택은 `gpt-6-sol` + `high`로 두고 실제 응답 metadata로 확인하여 manifest에 고정한다. 요청 별칭을 공급자 모델 ID로 오인하지 않는다. high reasoning, 도구·네트워크·시간 제한·모델 버전은 세 조건 동일.
- 본 비교 3은 `harness-auto-sol-controlled`: PM·구현·리뷰·대리 사용자까지 동일 Sol-high. 원본 하네스의 모델 조합을 변경한 이식 조건임을 표시한다.
- `3-cheap-workers`는 **별도 후속 조건**. 워커 모델·단가·라우팅 규칙을 사전 동결하고 본 실험 표에 합치지 않는다. 원본이 저가 워커를 기본 사용한다는 가정은 분석상 사실이 아니다.
- 2↔3 상세 입력은 파일 SHA-256으로 동일성 확인. 인터뷰로 얻은 추가 정보량, 질문 횟수·답변 길이를 별도 기록한다. 이는 하네스 전체 효과이며 절차만의 효과와 구별한다.
- 대리 사용자는 동결된 requirements/answer-policy만 읽는다. 다른 arm의 코드·실패 이력·개선안을 전달하지 않는다. 정답에 없는 질문은 `범위 밖; 기존 계약 내에서 결정하고 기록`으로 답한다. 구현 제안은 하지 않는다.
- 이번 준비 세션 및 fixture 제작 토큰은 setup 비용이다. 조건별 최초 입력을 작성/가공하는 유료 호출, PM·대리 답변·워커·리뷰·재시도·복구 토큰은 해당 조건 전체 비용에 포함한다.

## 진행과 반복

1. 기반 서버·fixture·판정기를 파일럿 검증한다. 업무 구현은 fixture에 넣지 않는다.
2. 원본 SHA, 모든 입력/판정/이미지 digest/seed/모델/자원/합격 기준을 동결하고 baseline 태그를 기록한다.
3. 각 arm/core를 **새 OS 격리 환경·새 세션**에 export한다. 동일한 빈 DB 초기 상태와 은행 journal을 준비한다.
4. 최초 입력부터 토큰 집계 시작. 첫 완성 선언 시 first-pass 검증 결과·토큰·품질을 보관한다.
5. 외부 평가자가 불변 판정기를 실행한다. 1은 한 항목, 2는 구조화 묶음, 3은 하네스 절차로 수정한다. 해당 run 안에서는 세션을 유지한다(매 턴 초기화하지 않음).
6. 모든 필수 기준을 처음 통과한 후보를 새 DB와 새 은행 상태에서 재검증한다. 통과 뒤 생긴 리뷰 수정도 다시 검증한다.
7. 리뷰·필수 검증·하네스 문서가 모두 완료된 최종 시점까지의 호출을 집계한다. 최종 보고용 통계 계산은 별도 analysis 비용이다.

파일럿 1회는 결과에서 제외. 사용자 지정에 따라 **각 조건 10회, 총30회** 독립 시행한다. core1..core10은 독립 반복 번호다. 순서는 core1=1→2→3, core2=2→3→1, core3=3→1→2, core4=3→2→1, core5=1→3→2, core6=2→1→3, core7=1→2→3, core8=2→3→1, core9=3→1→2, core10=3→2→1로 사전 고정한다. 10회는6의 배수가 아니므로 순서 불균형을 기록한다. 실제 부하는 동시에 실행하지 않는다.

각 시행의 `codex/docs/experiments/<arm>/core<N>/transcript.md`에 `1. 프롬프트` 전문과 `1. 결과물 분석`, 이어 `2. 프롬프트`와 `2. 결과물 분석`을 누적한다. 결과 원문·diff·검증 로그는 첨부 파일과 hash로 연결한다. PM·대리 사용자·워커 호출도 역할/세션을 붙여 빠짐없이 기록한다. 질문만 한 턴도 생략하지 않는다. 실행 전에는 NOT_STARTED만 쓰고 프롬프트를 실제 전달했다고 기록하지 않는다.

**한 시행 종료 → 모든 프롬프트/분석·사용량·검증 문서 마감 → 해당 arm/core와 결과만 커밋 → 다음 시행** 순서다. 실패/상한 도달도 독립 커밋하며 성공으로 표시하지 않는다. setup 커밋과 본 시행 커밋을 분리한다. commit SHA는 결과 index에 연결한다. 커밋 전 중단한 실행은 동일 run 복구로 처리하고 새 독립 표본으로 세지 않는다. 동일 머신의 시간대·CPU governor·다른 작업 유무를 기록한다.

## 종료와 실패

성공 = acceptance의 모든 P0/P1, 전수 데이터 불변식, 고정 부하 SLO, 장애 복구, 레이어드 품질 기준 통과 + 필요한 리뷰와 기록 완료. k6 HTTP 200만으로 완료 판정하지 않는다.

안전 상한(실험 전에 고정): run당 전체 input+output 2,000,000 tokens, 벽시계 8시간, 외부 피드백 30회. 먼저 도달하면 `CENSORED_BUDGET/TIME/TURNS`, 실패 산출물도 보존. 성공까지 무한 실행하거나 실패 arm을 통계에서 삭제하지 않는다. 실제 호출 종료 전 사용량 지연 때문에 상한을 초과하면 초과분도 기록한다.

평가기/fixture 오류는 `INVALID_INFRA`로 중단하고 비용은 보존한다. 판정 기준 변경 시 새 protocol version으로 **모든 조건 재실행**한다. 특정 arm만 느슨한 기준으로 통과시키지 않는다.

## 결과 표

`run_id, arm, core, provider, actual_model, effort, baseline_sha, contract_sha, harness_sha, cache_status, first_pass_pass_rate, final_status, total_input, cached_read, cache_write, output, reasoning_subset, total_tokens, estimated_cost, billed_cost, elapsed_s, feedback_rounds, quality_score, max_sustainable_rps, p95_ms, pool_wait_ms, peak_rss, throttle_s`.

총 토큰 중앙값·범위·성공률과 first-pass/final 정확도를 함께 보고한다. raw tokens는 할인 전 작업량이며 실제 결제 비용과 다르다. 완성도는 기능·성능·설계 세 축으로 공개하고 합성 점수 하나로 결함을 숨기지 않는다. 10회 표본의 불확실성을 표시한다. 모델 간 tokenizer가 다르므로 이후 Claude 실험은 비용·완료율 중심으로 병기한다.

## 실행 제어 확정

후속 사용자 합의: 세 조건 모두 별도 Codex CLI/컨테이너로 실행한다. 3번은 goal 자동계속을 사용하지 않는다. 외부 실행 관리자가 PM과 대화하듯 exec/resume로 질문 응답·명세 합의·검증 피드백을 전달한다. 하네스 auto는 명세 합의 뒤 자율 구현을 뜻하며 무조건 무인 goal을 뜻하지 않는다. 공급자 캐시는 observed-cache로 계측하고 완전차단이라고 주장하지 않는다.
